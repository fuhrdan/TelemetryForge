# Formal Verification

TelemetryForge v2.5.0 adds explicit formal models for the safety boundaries introduced by the Durable Edge releases. The purpose is not to decorate the repository with TLA+ syntax. The models state what the system is allowed to do, then CI explores finite state spaces and fails if a safety invariant can be violated.

## What is modeled

Four protocol slices are modeled independently:

1. **Durable ingest** — local fsync, client acknowledgement, downstream delivery, and compaction.
2. **Replicated durability** — origin persistence, peer durability quorum, downstream delivery, and replica release.
3. **Mesh failover** — eligible route ownership, forwarding attempts, failover, and terminal no-route behavior.
4. **Cryptographic lineage** — linked records, segment sealing, post-seal tamper, verification, and rejection.

The source specifications are in `formal/*.tla`, with finite TLC model configurations in `formal/models/*.cfg`.

## Safety invariants

The v2.5 release checks these core statements:

### Durable ingest

- a successful client acknowledgement always has durable evidence;
- an acknowledged but undelivered event remains in the local durable set;
- WAL compaction cannot happen before downstream delivery.

### Replicated durability

- replicated-mode acknowledgement requires the configured quorum abstraction;
- a pre-release quorum includes the origin durable copy;
- an acknowledged, undelivered event retains quorum;
- replica release only follows downstream delivery.

### Mesh failover

- one delivery never revisits a previously attempted owner;
- a terminal routing failure means no eligible candidate remains;
- delivery success and terminal routing failure cannot both be true.

### Cryptographic lineage

- verified sealed history is not tampered in the model;
- tampered sealed history cannot verify;
- rejection is associated with detected tamper;
- a segment seal cannot exist without a committed record chain.

## Two independent executable layers

TLA+ is the human-readable protocol specification. TLC checks the finite models in CI with the declared `tla2tools.jar` release plus an exact repository-pinned SHA-256 digest. Because the upstream v1.8.0 tag is a rolling prerelease channel, unexpected asset changes fail closed until reviewed.

The repository also contains a dependency-free Go checker:

```bash
go run ./cmd/formalcheck
```

It explores the equivalent bounded protocol states and emits counts for explored states, transitions, and checked invariants. This gives normal Go CI a second executable guardrail and makes proof evidence available without requiring the Java/TLA+ toolchain.

Save a machine-readable report with:

```bash
go run ./cmd/formalcheck --output formal-check.json
```

## Property-based schedule testing

`internal/formal` includes a Go fuzz target that interprets generated bytes as adversarial protocol schedules. The fuzz target repeatedly attempts persistence, replication, acknowledgement, delivery, and release actions and re-checks the durability invariants after every step.

CI runs a bounded fuzz session on every change. The exhaustive checker remains the stronger finite-state result for the current abstraction; fuzzing is additional implementation-side pressure, not a replacement for model checking.

## Operational proof

The `formal-verification` operational proof requires both:

- the Go bounded checker; and
- TLC model checking of all four TLA+ modules.

Successful runs emit the usual `.tfproof.json` plus the raw model-check report and logs.

```bash
TLA2TOOLS_JAR=/path/to/tla2tools.jar proof/formal-verification.sh --execute
```

## What v2.5 does not prove

The formal claim is intentionally narrow.

v2.5 does **not** prove:

- that a network partition eventually heals;
- that Kafka eventually accepts an event;
- that disk or hardware never permanently destroys every durable copy;
- that the Go implementation is free of all bugs;
- that cryptographic primitives themselves are mathematically proven here;
- exactly-once delivery;
- unbounded liveness of a global multi-cloud deployment.

The models prove safety properties over finite abstractions under their stated transition assumptions. Production evidence still requires implementation tests, race detection, integration tests, and operational proof.
