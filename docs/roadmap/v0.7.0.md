# v0.7.0 Development Plan

**Theme:** Kubernetes horizontal scaling + Cardinality Firewall

v0.7.0 should prove that the architecture can scale across replicas while
introducing the first telemetry-cost protection feature.

## Workstream A: Kubernetes

### Deliverables

- `deployments/kubernetes/base/` manifests
- gateway Deployment + Service
- worker Deployment
- dashboard Deployment + Service
- ConfigMaps for non-secret runtime configuration
- Secret references for database/Kafka credentials
- readiness/liveness probes
- CPU/memory requests and limits
- HorizontalPodAutoscaler examples
- PodDisruptionBudgets
- namespace and optional ingress example

### Scaling documentation

Document the relationship:

```text
Kafka partitions >= useful active consumer-group replicas
```

More worker pods than available assigned partitions do not create useful Kafka
consumer parallelism. Internal worker concurrency is a separate control.

### Acceptance criteria

- manifests render/validate in CI
- gateway can run with more than one replica without process-local correctness
  assumptions
- workers use one shared consumer group
- dashboard SSE remains correct through shared durable storage
- shutdown/probe behavior is documented

## Workstream B: Cardinality Firewall

### Detection model

Track approximate unique values for metric/tag dimensions inside a bounded time
window. Flag dimensions whose observed/projected cardinality crosses policy.

Initial dangerous-value heuristics should include identifier-shaped keys such
as:

```text
session_id
request_id
trace_id
user_id
order_id
uuid
```

Heuristics must create a finding, not silently destroy data.

### Policy actions

The first policy model should support:

- `allow`
- `drop_tag`
- `quarantine`

Quarantined telemetry must retain enough evidence to understand what was
blocked and why.

### Dashboard

Add a Cardinality Firewall panel showing:

- source / metric
- risky dimension
- observed unique count
- projected growth
- policy action
- reason
- first/last seen time

### Acceptance criteria

- deterministic unit tests for estimators/policy decisions
- bounded memory usage for cardinality tracking
- no raw high-cardinality value is copied into logs unnecessarily
- human-readable policy documentation
- ADR for estimator/policy architecture
- demo traffic that intentionally triggers a cardinality warning

## Out of scope for v0.7.0

- full billing-dollar estimates
- AI diagnosis
- arbitrary policy DSL
- Terraform cloud provisioning
- production authentication/tenant model

Those remain later roadmap items.
