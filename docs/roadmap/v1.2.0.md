# v1.2.0 Delivered Scope

**Theme:** Distributed Cardinality Intelligence.

## Problem closed

v1.1 production workers still held Cardinality Firewall estimates inside each
process. Multiple replicas could therefore under-estimate a stream split across
Kafka partitions.

v1.2 moves production estimator state into a mergeable shared hourly model.

## Delivered

### Shared state

- tenant-aware active/shadow HLL state
- 64 fixed HLL registers
- exact first 16 unique hashes
- atomic register maximum merge
- hourly policy windows
- seven-day TimescaleDB retention
- no raw tag-value persistence

### Forecasting

- observed unique
- projected one-hour unique
- growth per minute
- top exploding dimensions

### Budgets

- policy-as-code `budgets` array
- tenant-wide wildcard budgets
- source-pattern budgets
- series-limit / warning / critical settings
- active/shadow budget status
- advisory-only behavior

### Surfaces

- `GET /api/v1/cardinality/state`
- `GET /api/v1/cardinality/budgets`
- `telemetryctl cardinality top`
- `telemetryctl cardinality budgets`
- dashboard Distributed Cardinality panel
- dashboard Series Budgets panel

## Safety invariants

- Replay/cost analysis never touches production shared state.
- Budget crossing never silently destroys telemetry.
- Shared state stores hashes/registers, not raw tag values.
- Tenant identity remains part of every state key.
- A dependency outage does not silently change enforcement to replica-local
  semantics.

## Deliberately deferred

- batched HLL delta flushing
- Redis/dedicated cardinality service
- cross-region consistency architecture
- adaptive sampling based on budget pressure
- vendor-specific billing estimates

These belong to later scale/sampling milestones rather than being hidden inside
v1.2.
